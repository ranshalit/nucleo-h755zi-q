I read through the full `usb_debug.md` (46 steps — impressive log, by the way). Here's where things actually stand and what's worth trying next.

**Where you left off:** Host-mode enumeration reliably fails with a hardware-reported `TXERR`/"device not responding" on the very first control transfer, *only* under Zephyr's runtime. An identical bare-metal HAL-only harness (same board, same silicon, same cable, same camera) succeeds instantly and repeatedly. You've ruled out essentially everything at the configuration level: clocks, FIFO sizing, pinmux, VBUS, ID pin, PWR, reset timing, IRQ masking, Ethernet/AHB contention, CM4 contention, cache/MPU, poll-vs-interrupt servicing style, and even jittered retries. You also found the same "control-plane fine, periodic/timing-sensitive data-plane fails" pattern in the UAC2 isochronous device-mode test — a real signal that this is a systemic Zephyr/STM32-DWC2-glue issue, not device- or board-specific.

Given that, a few concrete things you haven't tried yet that would actually move the needle:

**1. NVIC priority of `STM32_HCD_IRQ` vs. everything else** — you tested poll-mode vs. interrupt-mode, but never swept priority itself. Set it to the highest priority in the system (0) and re-test. If a `TXERR` is really "device response arrived a few µs too late for the core's internal state machine," a lower-priority USB IRQ getting delayed by something else (even briefly) while the core's internal receive-buffer/RxFIFO-drain logic is time-sensitive could plausibly produce exactly this symptom without ever showing up as a "stuck" register in your polling snapshots.

**2. Actually get a scope/analyzer on D+/D-.** You've flagged this as the most conclusive missing step in the doc itself, more than once. Even a cheap FS-capable USB analyzer (Beagle 12, or a logic analyzer that can decode USB FS at ~48+ MHz sample rate — your software GPIO capture topped out at ~30 MHz and you already flagged that as borderline/possibly not trustworthy through the AF10 mux) would tell you definitively whether the host ever transmits a valid SETUP token on the wire during the Zephyr-failing case, and whether the device replies at all. This is the one test that can't be argued around by more register reads.

**3. Re-check `GUSBCFG.TRDT` (turnaround time) explicitly.** ST's HAL computes this from AHB clock via `USB_SetTurnaroundTime()`. You've confirmed `GUSBCFG=0x20001440` matches between bare-metal and Zephyr bit-for-bit at the same clock — so this is likely already ruled out — but worth explicitly decoding bits [10:7] and cross-checking against RM0399/RM0433's recommended TRDT table for your exact `AHB_CLK`, since a marginal-but-technically-"matching" value could still be borderline given real component tolerances (temp, HSI48 trim) that bare-metal's shorter/less complex boot might not stress the same way.

**4. Try a known-simple, low-power device** (a basic USB keyboard/mouse) instead of the camera, since you've now confirmed the exact same board model enumerates keyboard/mouse fine on someone else's ST Community thread. If a mouse enumerates on your board under Zephyr where the camera doesn't, that reopens the device-current-draw/VBUS-droop angle even though `PG7_nFAULT` never trips (a droop under threshold doesn't need to trip hard-overcurrent).

**Pragmatic fallback:** Steps 45–46 already show MSC/CDC-ACM/bulk-only device-mode is rock solid on this board under Zephyr. If the actual goal is a demo rather than pinning down this specific DWC2 host-mode bug, that's your reliable path — Host mode + isochronous both sit on the same still-unidentified periodic-transfer gap in Zephyr's STM32 DWC2 glue, and that's arguably worth reporting upstream (with your bare-metal vs. Zephyr repro) rather than continuing to chase it solo.
